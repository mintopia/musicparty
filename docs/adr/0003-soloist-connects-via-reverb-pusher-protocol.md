# Soloist connects to Music Party over Reverb using the Pusher protocol

Soloist's relay dials out using raw JSON over WebSocket, and Reverb only speaks the Pusher protocol. We chose to add Pusher-protocol support to the Soloist proxy. Its connection then joins a private Reverb channel for the Player, authenticated with a Player Token, and Music Party reads the Player's messages from inside Reverb. We did not run a separate raw-WebSocket server in Music Party, which would be a non-first-party component and another process to operate. We also did not have Music Party dial out to Soloist, which breaks behind NAT and inverts the intended "Soloist connects in" model. Both projects are ours, so changing Soloist was the cheaper side.

Clients stay simple. Soloist, and any future integration of the same kind, wraps its own native frames in Pusher client events without changing them. Music Party has one adapter per Player that parses them. Reverb only validates and hands off to queued jobs, and no domain logic runs inside the Reverb process. The channels and events are described in an AsyncAPI spec, with the same CI check for undocumented broadcasts that ADR-0002 sets up for HTTP.
