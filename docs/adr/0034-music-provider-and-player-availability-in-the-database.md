# Music Provider and Player availability lives in the database; Spotify credentials come only from provider settings

Spotify is missing from the Create Party Music Provider list. `SpotifyMusicProvider` and the Polling, Browser and Soloist Players exist, and all three Players accept only Spotify. But `config/musicparty.php` `music_providers` lists only `fake`, and `PairingCatalogue` and `StorePartyRequest` read only that config. Turning a Music Provider or Player on or off therefore means editing a PHP file and redeploying.

Spotify credentials are also split. Login and linking read the `spotify` and `spotifysearch` social provider rows through `SocialProvider::getSetting()`, which an admin edits under `/admin/providers` (encrypted by the `SettingValue` cast, masked, audited). `SpotifyApi`, `HostAccountTokens::requestRefresh` and `SearchCredentials` instead read `config('services.spotify*')`, which only the environment fills. Credentials saved in the admin UI never reach search, Track lookup, playback or token refresh, so an install configured through the UI alone fails with `ProviderUnavailableException`. v2 read Spotify credentials from the database everywhere.

Under Octane, `config()` is fixed when a worker boots. The players spec requires a change of Player to reach every web and background worker without a restart, and the music-provider spec already says a Music Provider whose credentials are missing cannot be selected for a Party.

We considered three alternatives:
- **Register and enable in the config file** (add `spotify` to `music_providers`, as today). This is the smallest fix, but every on/off change needs a deploy and a worker restart, and the file cannot tell whether credentials exist.
- **Env-only flags and credentials** (`MUSICPARTY_PROVIDERS=spotify`, `SPOTIFY_CLIENT_*`). This works for one operator, but it keeps the split with the admin UI, needs a restart, and contradicts the admin spec that credentials are edited and stored encrypted by admins.
- **A full database registry** (a table of provider and player classes). This lets admins add rows that point at classes. It moves code wiring into data, lets a row name a class that does not exist, and adds a table for something only a deploy can change anyway.

Decision:
- **Code registers, the database enables.** `config/musicparty.php` `music_providers` and `players` stay the registry of what exists, with label, class and, for a Music Provider, the social provider codes whose credentials it requires (`spotify` requires `spotify`). `spotify` is added to that registry. The registry no longer decides what is offered.
- **One enabled flag per Music Provider and per Player** is stored as a `settings` row (`music_provider.<id>.enabled`, `player.<kind>.enabled`, boolean) and read through `Setting::fetch`, which is cached in the shared cache store and cleared by `SettingObserver`. No new table is added. A missing row means disabled. A data migration writes rows that enable `spotify`, `fake` and the three Players, so an existing install keeps working.
- **Available means enabled and configured.** A Music Provider is offered and accepted only when its flag is on and every social provider it requires `isConfigured()`. A Player is offered only when its flag is on and it has Compatibility with the chosen Music Provider. The social provider's own `enabled` flag still governs login and linking only. `PairingCatalogue` reports availability; `StorePartyRequest`, `CreateParty` and `ChangePartyPlayer` validate against it.
- **The Fake Music Provider is offered only when the app environment is `local` or `testing`**, whatever its flag says. It is never offered in production or any other environment. Its registry entry and class stay, so tests keep using it.
- **Disabling never breaks a running Party.** A Party whose Music Provider or Player is disabled afterwards keeps working with it. Disabling stops new Parties choosing it and stops a Host switching a Party to it. A Host can always keep the current pairing. The admin page shows how many Parties use each one before it is disabled.
- **Spotify credentials come only from provider settings.** `SpotifyApi`, `HostAccountTokens` and `SearchCredentials` read the client id and secret from the `spotify` and `spotifysearch` `ProviderSetting` rows through one Identity reader. The reader is a scoped container binding, so each web request and each queued job reads the current values once. Nothing at runtime reads `services.spotify.client_*` or `services.spotifysearch.client_*`. `SPOTIFY_MARKET` is not a credential and stays in config.
- **Environment variables are a first-boot seed only.** `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, `SPOTIFYSEARCH_CLIENT_ID` and `SPOTIFYSEARCH_CLIENT_SECRET` stay in `config/services.php` for `providers:seed`, which fills empty provider settings and never overwrites them. An architecture test fails if any other code reads those keys.
- **The admin UI reuses the existing pages.** The admin Settings page gains Music Providers and Players tables in the same card, table and status-pill style as Social Providers (v2 look), each with an Enable or Disable action. Every change is audited (`music_provider.enabled`, `music_provider.disabled`, `player.enabled`, `player.disabled`), and the Admin API gains the same actions.

Consequences: Spotify appears once an admin has saved its credentials, with no deploy and no restart. Toggles and credential changes reach every Octane worker and Horizon job on the next request or job, at the cost of one cached read per toggle and one database read per credential set per request or job. Installs that relied on env credentials alone must run `providers:seed` once (the migration notes and README say so), or Spotify becomes unavailable until they do. Tests that set `config('services.spotify.*')` move to a helper that writes provider settings. Adding a new Music Provider or Player is still a code change plus a registry entry, and it starts disabled until an admin enables it. This amends the music-provider spec's Spotify requirement, which said search uses instance credentials, only in where those credentials are read.
