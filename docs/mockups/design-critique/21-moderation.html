Moderation: Flagged Requests and Rules

Flagged Requests, bulk approval, Rules and the moderator view, with combined search instead of filter sidebars (#426, #417; U5, U7). AI reviews, the third tab, is on the next sheet.

Flagged Requests Changed

The page is titled Moderation and the tabs read Flagged Requests (3), Rules and AI reviews. Each flagged Request says why it was held, with a link to the rule or AI review, and has large Approve and Reject buttons. The list is full width, the same width as Rules and AI reviews.

  • Title is "Moderation"; the tab is "Flagged Requests" with the count, as in the sidebar badge. Today the page has no h1 and the tab says "Flagged". #417, #425.
  • The reason is on every row: the Rule that matched (Artist name is Rick Astley) or the AI review criterion with its confidence and reason, each linking to the source. A-H7.
  • Approve and Reject are 44px buttons on every row instead of small buttons. Approve is green, Reject outlined red; no other filled button competes. A-H7.
  • Bulk select: a header checkbox selects all; with a selection the header becomes "2 selected · Approve 2 · Reject 2 · Clear selection". A-H7.
  • The four-field filter sidebar is replaced by the combined search with chips for what held it back. #426, U7.

Empty and not held Changed

When nothing is waiting, the page says so. When the party does not hold Flagged Requests at all, a notice explains why nothing waits here and offers the fix in the same place.

  • "Nothing waiting for approval" replaces "No flagged requests". The tab and sidebar badge drop their count.
  • The notice says "Flagged Requests aren't held" with a "Turn on approval" button (outcome of the setting "Hold Flagged Requests for approval"). It is the same notice AI reviews shows today. U4.

Rules Changed

Rules is the same page in the same width. The table gains an Action column (Flag or Reject), which the form had but the list hid, and the combined search with chips for state and action. Edit and delete are icon buttons with labels for assistive tech.

  • New Action column and plain "On/Off", "Exact/Pattern" words instead of ID, Yes and No columns. Rule ID is no longer the link; the edit pencil is. #426.
  • Add rule sits beside the search, not in a bar of its own. It is the only filled button.
  • Search matches type, value and notes; chips filter by state, action and pattern.

Edit rule and delete Changed

The form uses Settings' SettingRow layout and explains the two actions in a sentence each. Deleting names the rule and says what happens to Requests already flagged.

  • Action becomes two labelled choices with a sentence each (Flag for approval, Reject the Request) instead of a select. Today the page title says "Add rule" and the type select has no explanation.
  • The form is narrow (960px, centred) because it is a form, not a table. Delete rule lives in the footer, away from Save, and opens a dialog that names the rule.
  • The dialog reuses the app's ConfirmDialog markup. "Keep rule" is the safe label; "Delete rule" is the only red button.

Moderator view New

A moderator (Dev) sees Moderation but no Settings. Flagged Requests work as for the owner. Rules are read-only. Moderators are a new party role; the backend is a later ticket.

  • Sidebar: Dashboard, Queue, Search, Requests, Moderation, Members; no Settings. Moderators can approve and reject Flagged Requests and view AI reviews. U5.
  • Rules show a lock line instead of Add rule and the edit/delete column. They are still searchable.
  • Open question: may moderators edit Rules, or only the owner? Mocked as owner-only (read-only for moderators), per the brief.

Phone Changed

At 390px each flagged Request is a stacked card with the reason beneath and two equal 44px buttons. With a selection, the bulk bar pins to the bottom of the screen.

  • Approve and Reject sit side by side at full card width, the thumb-reachable pair. A-H7.
  • Rules become cards: type, value, action and state, notes beneath; no horizontal scroll.
